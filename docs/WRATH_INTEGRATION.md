# Wrath integration and update workflow

Wrath is the bundled execution and decision engine.
`Engine/Upstream/WrathCombo` contains the pinned upstream implementation,
including action replacement, Auto-Rotation, targeting, openers, IPC leasing,
configuration UI, and every PvE job evaluator. No job-by-job fallback
implementation is used.

`ReadOnlyRuntime` is retained as the public bridge name, but it now hosts the
complete engine. Live execution uses the upstream hooks and controllers.
Suggestion forecasting temporarily enters a thread-local `PredictionContext`;
only inside that context do the existing guards prevent configuration writes,
retarget registration, item use, movement, spellbook assignment, and automatic
casts. The execution engine and the overlay therefore share one configuration
and one rule set without forecast calculations mutating live game state.

Wrath configuration is serialized inside VieriRotationHelper's configuration.
On first migration the last separate `WrathCombo.json` is imported if present;
the legacy file is never deleted or rewritten. The integrated engine registers
the exact `WrathCombo.*` IPC names and uses WrathCombo.API 0.5.7, so existing
automation clients continue to use their normal leases and configuration calls.
If the separate Wrath Combo plugin is still loaded, the suite refuses to create
a second engine instance and displays a reload instruction instead of competing
for the same hooks and IPC names.

WrathSwitch is embedded as a dependency with its exact `/wrathswitch`, `/ws`,
and `WrathSwitch.BeginAutomation` contracts. Its configuration is likewise
imported once and then saved as part of VieriRotationHelper's root configuration.

The Hilda-derived UI remains separate. Hotkey resolution accepts only a button
that currently resolves to the suggested action. Future icons are generated by
re-running the selected Wrath evaluator after each action against an isolated
shadow timeline. That timeline advances combo state, the GCD/weave window,
action history, cooldowns, and charges without changing game state or Wrath's
live history. Ordinary consumables
have item icons and real item-hotbar keys; they are never auto-used. PvP and
special pomander buttons are not represented as ordinary spell suggestions.

## Source pin

`upstream/wrath.lock.json` records the exact upstream repository, version, and
commit used by the embedded rules. Do not change the pin without auditing and
testing every affected job.

## Updating

1. Check out the new Wrath source revision.
2. Run `scripts/Audit-WrathUpdate.ps1 -WrathPath <checkout>`.
3. Review every changed preset, action/status/gauge definition, job helper,
   simple/advanced rotation, and shared combat helper listed by the report.
4. Update the vendored sources, preserving/reviewing every prediction guard and
   hosted-configuration/IPC adaptation;
   update `JobCatalog`, `upstream/engine.lock.json`, and the source pin together.
5. Build and run tests. Every supported combat job must retain both ST and AoE
   real evaluator classes/entry points, not merely display mappings. Run
   `scripts/Test-Integration.ps1` for executable hotkey/visual tests and source
   safety/coverage checks. These are not substitutes for live combat testing.
6. Check representative combat with consolidation on, consolidation off,
   Auto-Rotation on/off, automation leases, job/level changes, rebinding, and all
   three bar modes. Record
   which live scenarios were actually tested; never claim all-job live parity
   based on static coverage or a successful compile.

The audit is deliberately machine-readable (`wrath-update-audit.json`) so a
future Codex request can identify exactly which jobs and shared systems changed
instead of manually rediscovering the integration surface.
